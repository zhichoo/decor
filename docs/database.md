# PostgreSQL 数据库

业务基线为 `db/schema.sql`，依据已恢复的 PostgreSQL 18 结构整理，包含 `sources`、`videos`、`extraction_runs`、`claims` 四张表，以及原有全部字段、默认值、索引、唯一约束、检查约束和外键。基线不含用户数据、连接凭据、原服务器 owner、`pg_dump` 元命令或 `CREATE SCHEMA public`；全新数据库自带 `public`。基线首先在 `public` 安装 `pg_trgm`，供原有 GIN 模糊搜索索引使用。

## 初始化空库

先创建独立 PostgreSQL 18 数据库并安装后端 Python 依赖。目标账号需有连接数据库、在 `public` 建表、安装 `pg_trgm` 的权限。连接只从环境变量 `DATABASE_URL` 或本地 `backend/config.local.json` 的同名字段读取；环境变量优先。无需配置或导入后端 server。请先核对目标数据库，脚本不会自动创建数据库。

在仓库根目录运行：

```sh
python scripts/init_db.py
```

初始化在同一事务中创建扩展、表、索引及约束，任何一步失败都会回滚。脚本用数据库内的事务级 advisory lock 串行化本脚本与种子命令。

- 空库：创建业务基线，随后校验结构并提交。
- 四张业务表全部存在：只检查 `pg_trgm`、字段类型/可空性/默认值、约束定义及有效性、索引定义及有效性，通过后跳过。允许额外字段、约束和索引；不会修改现有结构或扫描、更新业务数据。
- 仅部分业务表存在、同名对象不是普通表，或现有业务结构不符合基线：报错退出，保持数据库不变。
- 没有业务表但已有其他非系统表、视图、序列等：拒绝初始化，避免误操作其他应用数据库。扩展自身拥有的对象不算应用数据。

校验要求基线对象名称和 PostgreSQL 输出的定义一致；改名或结构演进需要人工审查，不会由初始化脚本自动迁移。脚本无重置、删表、删数据选项。恢复备份应走单独的恢复流程；不要将已有数据的数据库当作空库处理。

## 旧数据库结构升级

恢复旧备份后，先运行兼容迁移，再检查数据库结构：

```sh
python scripts/migrate_transcript_jobs.py
python scripts/migrate_claim_context.py
python scripts/init_db.py
```

迁移仅补充缺失字段，不改写现有业务数据；可以重复执行。`./dev.sh start` 会自动执行这些步骤。

`dev0.2` 新增可空的 `claims.author_stance`、`content_type` 和 `source_quotes`，分别保存作者态度、主要内容类型和原文连续引句。旧字段 `stance` 保留兼容用途，不改变旧约束。旧卡片的新字段保持空值，不猜测态度、不自动生成引句，也不批量调用模型。新提取使用 v6 提示词；网页按作者态度展示，引用不等于事实核验。

## 可选演示数据

初始化不会自动运行种子。需要演示内容时明确运行：

```sh
python backend/seed_data.py
```

种子连接采用相同配置规则，先校验业务基线，再在一个事务中写入演示数据：4 个来源、1 个视频、4 条观点，无 extraction run。所有来源、视频、观点 ID 均以 `demo_` 开头。写入只使用 `INSERT ... ON CONFLICT DO NOTHING`，重复运行不会更新已有行，包括人工编辑后的演示行。

视频 `source_url` 仍是原示例链接，因此已恢复数据可能占用这个 URL。发生冲突时，不覆盖真实视频，不把演示观点挂在真实视频上；只有存在预期演示 ID、相同 URL、相同来源且未被软删除的视频，才可接收演示观点。视频不满足这些条件时，跳过该视频对应观点。演示来源仍可独立插入。

视频采用约束允许的 `claims_extracted` 状态；`has_transcript` 和 `transcript_length` 根据去掉首尾空白后的文案计算，非空文案记录转写创建时间。原示例发布日期只有 `2026`，不足以表达准确时间，因此保留 `published_at` 文本，`published_at_ts` 为 `NULL`。完整日期/时间按后端规则解析为带时区时间，无时区的完整日期按 UTC 处理。

种子包含原示例的文案和观点，仅用于明确选择后的本地演示；初始化空库时不会加载这些内容，也不会连接采集或 AI 服务。
