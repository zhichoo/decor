# 如何选择全包装修公司：需求与开发计划

日期：2026-11-13

状态：开发前方案，尚未实现。本文确定一个装修问题指南的首版范围，不启动素材采集、模型调用或线上发布。

## 1. 目标与核心判断

帮助准备选择全包服务的业主完成：确认需求 → 初筛候选 → 比较报价与交付 → 核对签约条件。

更关键的问题是：同样叫“全包”，各家的包含范围、实际执行团队、追加费用和责任边界是否相同，用户能否取得可核对的书面约定。只看总价、品牌规模、流量或案例照片，无法回答这些问题。

首版提供“怎么比较、问什么、留什么材料”的指南。有充分来源和条件时给出具体建议；不足时列出待确认问题。不给具体公司排名，不承诺识别所有风险，不把视频观点改写成行业标准。

面向普通住宅家庭；毛坯、旧房翻新和局部改造的区别按内容需要说明，不设统一预算、付款比例或工期阈值。

## 3. 首版页面与阅读路径

在知识库上方增加紧凑的“专题指南”入口，首个专题为“选全包装修公司”。沿用当前原版样式与主题切换约定，不新增一套视觉系统。

页面结构：

1. 标题与最近内容更新日期。
2. 页内步骤导航：定范围、筛公司、看交付、比报价、核合同、留交接。
3. 各步骤默认显示少量核心行动和问题；相关知识卡、原文及补充项按需展开。
4. 页面底部提供“签约前核对清单”和“复制清单”。

条目使用统一的小结构：**问什么 → 核对什么材料 → 哪些条件会影响判断**。需要解释时再展示简短理由与来源，避免每项重复免责声明。

知识卡沿用现有卡片和关联弹窗。查看来源先进入应用内视频详情；返回保留指南步骤、展开状态和滚动位置。手机端单列、页内导航可横向滚动，不使用宽对比表作为主要阅读布局。

全页统一说明一次：“视频内容是作者观点；核对清单用于收集信息，不等于公司认证或合同法律意见。”具体条目仍须保留实质性的适用条件。

## 4. 指南内容范围

下面是需要设计和收集依据的问题，不代表已有资料已经回答全部问题，也不直接当作事实性建议发布。

| 步骤 | 用户要做的决定 | 核心问题 | 希望取得的材料 |
| --- | --- | --- | --- |
| 定范围 | 全包是否适合自己，哪些项目自己负责 | 能投入多少时间；设计、主辅材、定制、设备、家具家电分别由谁提供；旧房拆除与特殊施工是否包含 | 自己的需求清单、双方责任范围表 |
| 筛公司 | 哪些候选值得进一步接触 | 签约、施工、收款主体分别是谁；经营状态和适用资质如何核对；案例是否对应相似房型、预算和改造类型 | 主体名称、公开信息查询线索、书面服务说明 |
| 看交付 | 谁会实际把工程做完 | 具体负责人是谁；团队、分包与更换如何约定；能否了解在建工地和已交付案例；问题由谁处理 | 团队与责任说明、经同意取得的现场记录、项目沟通安排 |
| 比报价 | 总价是否建立在相同范围上 | 面积与工程量口径、材料品牌型号规格、工艺和数量、包含与排除项、选配升级、拆除清运与保护、增减项确认方式 | 同口径报价、材料清单、图纸与工艺附件、变更规则 |
| 核合同 | 条件是否清楚到可以签约 | 付款节点对应什么成果；验收和整改如何约定；工期与延期、停工、退出及结算如何处理；口头承诺是否写入附件 | 合同及附件、付款与验收安排、变更和违约条款 |
| 留交接 | 后续验收和售后如何落实 | 隐蔽资料、竣工图、材料凭证、保修对象与期限、报修渠道和责任如何交接 | 交接目录、问题与整改记录、保修与售后文件 |

对比时先统一需求、范围和计量口径，再比较总价。示例只演示如何识别“报价不可直接比较”，不编造市场均价或所谓合理利润率。

涉及企业信息、资质、合同法律效果或投诉流程的条目，开发时必须记录适用地区、查询或文件日期和原始链接。企业登记状态只能说明对应公开记录，不能单独证明履约能力；具体资质要求不预设为全国所有项目统一。

## 5. 内容表达与证据

区分三种内容，展示措辞与数据结构均需对应：

| 类型 | 用途 | 发布要求 |
| --- | --- | --- |
| 核对问题 | 引导用户询问范围、责任、费用或交付物 | 可由编辑编写，明确是问题或待确认项，不伪装为来源结论。 |
| 来源观点 | 展示作者明确提出的建议、条件与不同意见 | 绑定有效卡片和内容指纹，保留作者、范围及来源入口。 |
| 有依据的建议 | 将证据用于明确场景下的选择行动 | 明确适用条件和支持依据；支持不足时改成核对问题，不输出确定推荐。 |

删除或修改引用卡片后，不能继续沿用旧结论。仅删掉来源链接、保留指南建议也不合格。不同观点保持可见，不按视频数量多数表决，不用同一作者的多条内容制造共识。

首版不新增 AI 二审、人工审批页、待审批库存或打分。内容编写和发布前的开发验收不变成逐卡业务审批流程。

## 6. 功能范围

### 首版必须有

- 一个可通过独立地址直接打开的指南：`#guide/all-inclusive-company`。
- 六步导航、简洁内容、相关卡片与相近／不同观点入口。
- 统一的签约前核对清单，可勾选、重置和复制；勾选状态只保存在当前浏览器，不产生服务端写请求。
- 清单状态标明“已核对 / 未核对”，不自动推导为“公司可靠”或“可以签约”。
- 私有应用与静态公开版均可阅读；公开版不显示内容编辑、管理员登录或公司资料上传入口。
- 引用失效检测、资料缺口输出、静态导出与返回位置兼容。

### 后续再考虑

- 本地比较少量候选公司的范围、报价和待确认项；先用文字差异，不设分数、星级或权重。
- 输入房屋状态、城市和预算范围后筛选相关条目；只做已知条件匹配，不生成缺乏依据的结论。
- 如确需记录真实公司报价、联系方式和合同，另行设计私有存储及导出隔离，不能混入公开快照。

首版不做公司库、推荐名单、点评社区、合同上传识别、在线法律审查、个性化 AI 问答或一套通用指南后台。

## 7. 技术设计：指南与业务低耦合

首版采用文件维护专题内容，不新增业务表、不改知识卡提取契约、不重提取全库。

建议文件职责：

| 位置 | 职责 |
| --- | --- |
| `content/guides/all-inclusive-company.json` | 专题内容、步骤、清单、引用与适用范围；纳入版本控制，不含真实用户和公司私有信息。 |
| `backend/guide_catalog.py` | 校验结构、解析有效引用、判断指纹变化，生成可公开的指南数据；不访问模型。 |
| `web/guides.js` | 渲染步骤、清单与导航恢复，通过显式接口复用现有卡片及来源操作，不复制卡片模板。 |
| `web/guides.css` | 专题布局，使用应用设计变量并限定到指南容器；切换主题时不改变业务状态。 |
| `scripts/check_guides.py` | 只读检查结构、缺失／变更引用与无来源建议，输出受影响条目。 |
| 现有 API 与导出器 | 私有应用增加只读指南查询；静态导出复用相同解析规则，将指南加入公开快照。 |

数据字段保持最少：

- 指南：`id`、`slug`、`title`、`schema_version`、`content_version`、`updated_at`、`scope`、`steps`、`checklist`。
- 条目：稳定 `id`、`kind`、`question`／`text`、`conditions`、`documents`、`claim_refs`、`external_refs`。
- 卡片引用：`claim_id`、内容指纹；只用于变化检测，不向读者展示指纹。
- 外部引用：原始链接、标题、发布机构或作者、适用地区、发布日期（未知可空）、核对日期；查询日期不得冒充发布日期。

既有观点关联指纹可复用，但应确认覆盖该条目依赖的引句、范围等字段；不足的字段增加专题指纹计算，不改已有关系的语义。

运行与导出规则：

1. 读取指南后，按同一数据库快照解析卡片引用和来源可见性。
2. 引用删除或变化时，不显示仍依赖旧证据的建议，改为简短的“资料待补充”；通用核对问题仍可保留。
3. 在管理员只读诊断或命令输出中列出具体受影响条目，不生成审批任务。
4. 结构错误阻止生成新发布产物，保留原产物；证据缺失按上述规则降级并报告，不要求补齐全部资料才允许发布问题清单。
5. 本地删除后，已上线静态站仍是旧快照，必须重新发布才更新。不能承诺离线静态站实时感知本地变化。

新快照采用显式兼容方式扩展，旧快照缺少指南数据时隐藏入口，不因可选字段缺失导致整个知识库无法加载。

## 8. 资料补齐计划

先整理现有候选，再围绕未回答的问题寻找资料。优先补齐：

1. 全包服务包含／排除范围与双方责任，尤其定制、设备、拆除、清运和保护。
2. 同口径报价与工程量、材料规格、变更增减项。
3. 实际团队、项目管理、现场核对和交付记录。
4. 付款、验收、整改、退出结算与售后约定。
5. 主体信息、适用合同示范文本和所在地官方公开说明。

优先近一年、非推广且有实际信息的素材；法律、合同及公共查询说明需核对当前适用性。保留原始发布日期和地区。视频按已有收录规则控制长度，无法取得有效文案或关键证据时跳过，不用标题与搜索摘要补成知识卡。

官方资料用于核对程序、术语与适用边界；视频用于展示作者经验和案例。首版需要引用官方网页时，先作为指南外部引用，不顺带开发通用网页采集器，也不把网页观点伪装成视频卡片。

不设“必须新增多少张卡”的完成目标。逐个确认六步的核心问题是否有可操作的内容、哪些仍需用户核实；资料不足时缩小结论范围。

## 9. 开发顺序与交付物

| 阶段 | 工作 | 可验收交付 |
| --- | --- | --- |
| A：内容样稿 | 整理现有候选，写六步问题、证据和缺口；优先打磨“比报价” | 一份可阅读的指南样稿和逐条引用清单；来源观点与编辑问题有明确区分。 |
| B：只读指南 | 实现内容结构、引用解析、指南页面和来源导航 | 本地可打开的完整阅读闭环；复用原卡片、关联与返回行为。 |
| C：清单与公开版 | 实现浏览器清单状态、复制、导出与旧快照兼容 | 桌面／手机可用，公开版仅在浏览器保存勾选，不向后端写入。 |
| D：补缺与验收 | 针对缺口收录资料，验证证据失效和部署 | 缺口记录、回归结果与可发布产物；用户明确要求发布时再上线。 |

先完成 A 再固化数据字段；B、C 不依赖所有素材补齐。暂不为一个专题搭建多指南 CMS，也不要求先完成全项目重构。

## 10. 验收标准

- 用户可从知识库进入专题，找到比较范围、报价、团队、合同与交接的具体问题及应取得的材料。
- “全包是否包含某项”明确要求核对书面范围，不以套餐名称代替结论。
- 来源观点能打开原卡和视频详情；返回恢复原步骤、展开状态与阅读位置。
- 条件不一致或来源意见不同，能看到差异；不输出“多数作者说过所以可靠”。
- 不出现无依据的付款比例、市场均价、品牌排名、普遍资质要求或合同法律结论。
- 删除引用卡、修改关键条件、原视频移入回收站但保留卡片、永久删除视频等情况，分别遵守现有可见性规则；依赖失效证据的建议不残留。
- 静态公开版的数据与私有应用使用同一解析规则，不含私有公司资料、密钥、内部诊断和管理入口；无后端 API 请求和服务端写请求。
- 清单勾选可恢复、可重置；浏览器禁用存储时仍可阅读和临时勾选，复制失败有明确反馈。
- 支持直接链接、刷新、浏览器前进后退、390px 手机宽度与键盘操作。
- 自动检查结构和证据引用；运行相关卡片、来源返回与公开导出回归。检查通过仅代表功能和引用约束成立，不等于作者观点得到事实认证。

首版成功的表现：用户能拿着清单与候选公司沟通，并看清尚未确认的范围和责任；不是获得一个看似精确的公司分数。
